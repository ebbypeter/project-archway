= Modelling Standards

== Properties are facts

Technology metadata is stored in `properties`, never as tags.

Mandatory on every software system (pipeline-enforced): `owner`, `capability`,
`lifecycle`, `criticality`.

Optional: `runtime`, `database`, `hosting`, `vendor`, `supportTeam`, `repository`,
`businessOwner`.

Lifecycle values: `Production`, `Under Upgrade`, `Retiring`.
Criticality values: `High`, `Medium`, `Low`.

== Portfolio categories

Every system belongs to exactly one portfolio category (Critical Apps, Market
Apps, Corporate Apps). It is declared as a `group` — which draws the boundary
on diagrams — and repeated as a tag, because Structurizr views cannot filter on
group. `make new-system` writes both. Categories are listed in
`models/shared/vocabulary.json` and enforced by the validator.

See `scale.adoc` for why categories, not a single landscape, are the unit of
estate-wide diagrams.

== Controlled vocabularies

`lifecycle`, `criticality` and `hosting` accept only the values listed in
`models/shared/vocabulary.json`; `capability` must have a matching page in
`docs/capabilities/`. These are pipeline-enforced because a typo in a property
does not fail anything on its own — it silently produces a wrong inventory
report.

== Tags are classifications

Only tags from `models/shared/tags/approved-tags.adoc` may be used
(pipeline-enforced). Never create technology tags such as `DotNet10`.

== Perspectives

Each system declares `Technology`, `Lifecycle`, `Ownership` and `Criticality`
perspectives summarising its properties, so viewers can overlay them on diagrams.

== Documentation

* System, solution and workspace documentation is AsciiDoc, wired in with `!docs`.
* ADRs use the adr-tools Markdown format (`docs/templates/adr.md.template`), wired in
  with `!adrs` at workspace level; integration and solution ADRs live in their
  asset's `adr/` folder.
